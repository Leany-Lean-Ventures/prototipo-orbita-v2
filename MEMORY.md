# Memória do Projeto — Órbita (Ademicon)

Registro de decisões, definições e aprendizados acumulados ao longo do projeto. Consulte este arquivo antes de iniciar qualquer trabalho novo — ele existe para não precisarmos re-explicar contexto a cada interação. Atualize sempre que uma decisão relevante for tomada (nova convenção, mudança de rumo, definição de escopo, correção de abordagem).

## Como usar

- Adicione uma entrada nova por decisão, na seção `## Decisões`, em ordem cronológica (mais recente no topo).
- Formato de cada entrada:
  ```
  ### AAAA-MM-DD — Título curto da decisão
  **Decisão:** o que foi definido.
  **Motivo:** por que essa escolha (contexto, restrição, pedido do usuário).
  **Status:** vigente | supersedida por [link/data] | revisar.
  ```
- Se uma decisão for revertida ou substituída, não apague a entrada antiga — marque `Status: supersedida por ...` e adicione a nova. O histórico de "por que mudamos de ideia" tem valor.
- Decisões de escopo muito específico de um módulo (ex: uma regra de negócio de uma tela) podem viver no próprio `PRD-XX` correspondente; aqui ficam decisões transversais ao projeto (stack, arquitetura, processo, ferramentas, convenções).

### 2026-07-26 — Bug de layout "containers desalinhados": CSS `transition` em `transform` brigando com o GSAP do `usePageEntrance`
**Sintoma:** o Dashboard (e também `/esteira` e `/configuracoes`) aparecia com os containers desalinhados — KPI cards menores e deslocados, coluna direita ~16px abaixo do gráfico, gaps visualmente irregulares. **Nenhum ajuste de grid/gap/flex resolvia**, porque o layout CSS estava correto o tempo todo.
**Causa raiz (provada por A/B test com Playwright):** `Card` com a prop `interactive` aplica `transition-[transform,box-shadow] duration-base ease-micro` (para o hover lift). O `usePageEntrance` anima `y`/`scale` — ou seja, `transform` — **nesses mesmos elementos**. As duas engines disputam a mesma propriedade: a transition CSS intercepta cada escrita inline do GSAP, o tween congela perto do valor inicial e **nunca chega ao estado final**, deixando um `transform` inline residual permanente (ex.: `translate(0px,16px) scale(0.97)` nos `.kpi-card`). Medição: com a transition em `transform` → todos os `Card interactive` travados; removendo `transform` da transition → todos em `matrix(1,0,0,1,0,0)`. Correlação de 100%: **todo elemento travado era `Card interactive`; todo elemento correto era `Card` simples** (no Dashboard, o mesmo tween `.dashboard-section` acertava os 3 cards não-interativos e travava os 3 interativos). Os valores congelavam em pontos ligeiramente diferentes a cada carregamento — era uma corrida, não um bug determinístico, o que explica por que parecia intermitente/insolúvel.
**Correção (em `src/hooks/use-page-entrance.ts`, conserta todas as páginas de uma vez):**
1. Resolve os elementos uma única vez com `gsap.utils.toArray(selector, scope.current)` em vez de passar strings de seletor — `onComplete`/`setTimeout` rodam **fora** da função do `gsap.context`, onde o escopo de seletor do `useGSAP` não se aplica (bug latente que existia no watchdog antigo).
2. `gsap.set(allEls, { transition: "none" })` antes de criar a timeline — desliga a transition CSS durante a entrada, aplicando mecanicamente a regra "não misturar".
3. `clearProps: "all"` no `onComplete` **e** no watchdog (agora incondicional) — o estado de repouso volta a ser 100% CSS, sem estilo inline.
**Efeito colateral corrigido de quebra:** o hover lift dos cards interativos estava morto — o `transform` inline deixado pelo GSAP vencia o `hover:-translate-y-0.5`. Agora volta a funcionar (verificado: `none` → `matrix(1,0,0,1,0,-2)` no hover).
**Regra a seguir daqui pra frente:** nunca animar via GSAP uma propriedade que tenha `transition-*` CSS ativa no mesmo elemento. Se um elemento novo precisar de entrada orquestrada **e** de microinteração de hover na mesma propriedade, ou anima um wrapper (GSAP no pai, CSS no filho), ou passa pelo `usePageEntrance`, que já neutraliza a transition durante a entrada. Isso é a aplicação literal da tabela "CSS puro vs. GSAP" do CLAUDE.md/design-system §7 — o custo de violá-la não é um glitch de animação, é **layout permanentemente quebrado**.
**Ajuste junto:** o `flex flex-col gap-3` da coluna direita do Dashboard virou `gap-6`, para o espaçamento ser uniforme (24px) entre todas as linhas e colunas da página.
**Status:** vigente. Validado: `tsc` limpo nos arquivos alterados, `npm run lint` só os 8 warnings pré-existentes, `npx vitest run` (3/3), e varredura Playwright — resíduo de transform = 0 em `/`, `/esteira` e `/configuracoes`; estável em 4 carregamentos seguidos; `prefers-reduced-motion` OK (conteúdo visível, sem transform residual); geometria do Dashboard com todas as linhas em `left=292/right=1560` e gaps 24/24/24.

### 2026-07-26 — Padrão de UI: coluna de ação "ver detalhe" em listas de item-resposta é sem título, ícone `Eye`, última coluna
**Decisão:** toda tabela de listagem cujo item representa um **registro/resposta já concluído** (uma visita registrada, uma prévia processada — não uma entidade cadastral como Unidade/PV/Consultor) deve ter uma **coluna final sem título** (`<TableHead />` vazio, "já é auto-explicativo") contendo um botão `Button variant="ghost" size="icon"` com o ícone Lucide **`Eye`** (nunca `FolderOpen` ou outro ícone de "abrir pasta/processo") — `aria-label` descritivo (`Ver respostas da visita a X` / `Abrir processo de X`), navegando para a página de detalhe/resposta daquele item. Corrigido em `PreviasPage.tsx` (trocado `FolderOpen` → `Eye`, removido o texto "Ações" do header da coluna) para não divergir do padrão agora estabelecido em `VisitasPage.tsx`.
**Por que a linha inteira não é mais clicável nesses casos:** ao contrário de Unidades/PVs/Consultores (onde a linha inteira é clicável — `tabIndex`/`onClick`/`focus-visible:ring`, convenção separada e ainda válida para listas de **entidades cadastrais**), listas de **respostas/registros** têm um botão explícito como único gatilho de navegação — o usuário pediu isso especificamente para deixar claro que "deve clicar" no ícone, em vez de depender de uma linha clicável não descoberta por padrão.
**Aplicar em:** qualquer lista nova de "itens já respondidos/processados" (ex.: uma futura lista de respostas de formulário, relatórios gerados). Não retroalimentar automaticamente em Unidades/PVs/Consultores/Ocorrências nesta rodada — o pedido do usuário mencionou Visitas + Prévias como exemplo concreto; Ocorrências continua usando modal + linha clicável até uma instrução explícita de migrar.
**Motivo:** pedido direto do usuário — "salvar o padrão do olho nas linhas de resposta na memória, quero que as listas de itens contenham ele daqui pra frente".
**Status:** vigente.

### 2026-07-26 — Padrão obrigatório de container de listagem: busca/filtros + tabela + paginação unificados num único `<Card>`

### 2026-07-23 — Mapa de Vínculos migrado de SVG cru para React Flow (`@xyflow/react`)
**Decisão:** `VinculosGraph.tsx` foi reescrito para renderizar sobre `@xyflow/react` (MIT, licença gratuita para tudo que usamos) em vez do `<svg>` desenhado manualmente. Pesquisa comparativa (`WebSearch` + `reactflow.dev`): descartado **Cytoscape.js** (estiliza nós via canvas/stylesheet próprio — perderia a reutilização direta dos ícones Lucide/`Badge`/tokens já usados) e **react-force-graph/d3-force** (simulação de física geraria posições instáveis, incompatível com o layout radial hierárquico já validado). React Flow venceu por manter os nós como componentes React de verdade.
1. **O que NÃO mudou:** `src/lib/mock-data/vinculos.ts` (derivação dos dados) e `src/lib/graph-layout.ts` (`computeRadialLayout` continua sendo o algoritmo de posição — React Flow só consome as posições `{x,y}` já calculadas, não faz auto-layout sozinho). `VinculosGraphPanel.tsx`/`VinculosListView.tsx` inalterados na lógica.
2. **Ganho de recursos "de graça" (core MIT, sem Pro):** zoom (scroll/pinch/botões), pan (arrastar o canvas), **drag-and-drop de nó** (`onNodesChange` + posições guardadas em estado local, sobrescrevendo o layout radial inicial só para os nós movidos), `<Controls />` (zoom in/out/fit view), `<MiniMap />` (colorida por tipo, mesma paleta `chart-1..4`) e arestas animadas (`animated: true` nas conexões do nó selecionado, tracejado em movimento — desligado sob `prefersReducedMotion()`).
3. **Nó custom único** (`GraphNodeChip.tsx`, registrado em `nodeTypes: { chip: ... }`, parametrizado por `data.node.tipo`): chip `rounded-lg border bg-card` com ícone-chip colorido — troca as formas geométricas do SVG antigo pelo padrão de ícone-chip que já é regra dura do projeto (CLAUDE.md, nunca stroke lateral). Foco visível nativo de `<div>` (`focus-visible:outline`), mais simples que o truque de `outline` em SVG que a versão anterior precisou.
4. **Pegadinha encontrada:** o `<MiniMap>` só desenha os retângulos dos nós se o objeto `Node` tiver `width`/`height` explícitos (ou já tiver sido medido via `ResizeObserver`) — sem isso, renderiza só a máscara do viewport, vazio. Corrigido setando `width`/`height` fixos por nível direto no objeto de cada nó (não só via CSS do componente).
5. **Arestas trocadas de `smoothstep` (cotovelos retos, "circuito impresso") para `simplebezier`** — mais adequado a um layout radial (curvas suaves entre nós em anéis) do que o roteamento ortogonal, que fazia mais sentido para fluxogramas em grade.
6. **Escala de layout:** `computeRadialLayout` ganhou um 3º parâmetro opcional `scale` (chamado com `2.4` no grafo) — os raios de anel foram calibrados para círculos pequenos de SVG; os chips do React Flow ocupam bem mais espaço real em px.
**Motivo:** usuário pediu explicitamente uma biblioteca "mais completa, com mais recursos, animação e interativa, com zoom e drag-and-drop" para dar acabamento profissional, depois de ver a primeira versão em SVG cru.
**Status:** vigente. Bundle JS subiu de ~446KB para ~507KB gzip (aceitável, mesma ordem de grandeza do que o ApexCharts já custava; sinalizado no aviso de chunk grande do Vite, que já existia antes). Validado via Playwright: zoom (botões e scroll), pan, arrastar nó, seleção nos 4 tipos, filtro por tipo, toggle "Ver como lista", navegação por teclado (Tab + Enter), `prefers-reduced-motion` (zero arestas animadas), zero erros de console.

### 2026-07-22 — Listas dentro de um card usam linhas empilhadas com divisor, nunca "card dentro de card"
**Decisão:** quando um `<Card>` contém uma lista de itens (alertas, ocorrências, ranking, qualquer "top N"), cada item vira uma **linha** dividida por `divide-y divide-border` no container pai + `py-3` (sem `space-y-*` nem `gap-*` entre itens) — nunca um sub-card individual (`rounded-lg border border-border p-3` por item). O padrão "card branco dentro de card branco" (visto em "Alertas que exigem ação" antes desta correção) fica murcho: pouco contraste, hierarquia visual confusa, ruído de bordas repetidas. Corrigido em `Dashboard.tsx` ("Alertas que exigem ação" e "Últimas Ocorrências") e em `AlertsPanel.tsx` (mesmo componente de alertas, reaproveitado no Sheet do header — sofria do mesmo problema).

Print do usuário confirmando o padrão desejado anexado nesta conversa.
**Quando usar `<table>` de verdade vs. `divide-y` numa lista de `div`s:** se o conteúdo tem múltiplas colunas alinhadas com cabeçalho (ex.: futuro "Ranking de Unidades" do Dashboard, listagens de Unidades/PVs/Consultores na etapa 4+), instalar o componente shadcn `table.tsx` (ainda não existe no projeto) e replicar as classes do V1 acima. Se é só ícone + rótulo + valor/ação por linha (Alertas, Ocorrências), `divide-y` numa lista de `div`s already resolve — não força uma tabela onde não há colunas de verdade.
**Motivo:** pedido explícito do usuário, com instrução de salvar como padrão permanente para reaplicar em qualquer lista futura dentro de um card.
**Status:** vigente. Regra adicionada ao `CLAUDE.md`.

### 2026-07-26 — Kanban drag-and-drop: solução definitiva para offset do DragOverlay com @dnd-kit
**Decisão:** ao usar `@dnd-kit/core` para um Kanban com colunas em scroll horizontal dentro de um layout com sidebar, o `DragOverlay` fica deslocado da posição do cursor. A solução requer **duas** correções complementares:
1. **`snapCenterToCursor`** (de `@dnd-kit/modifiers`) no `<DragOverlay modifiers={[snapCenterToCursor]}>` — centraliza o overlay visual no ponteiro, eliminando offset causado por scroll containers e CSS transforms do layout.
2. **`collisionDetection={pointerWithin}`** (de `@dnd-kit/core`) no `<DndContext>` — faz a detecção de colisão usar a posição do ponteiro (não o rect original do item arrastado) para determinar a coluna de destino. Sem isso, o highlight da coluna fica deslocado à direita.

Ambos são necessários juntos. `MeasuringStrategy.Always` no `measuring.droppable` complementa mantendo as medidas dos droppables atualizadas durante o drag.

Configuração final no componente (`src/components/esteira/KanbanBoard.tsx`):
```tsx
import { pointerWithin, MeasuringStrategy } from "@dnd-kit/core";
import { snapCenterToCursor } from "@dnd-kit/modifiers";

const measuring = { droppable: { strategy: MeasuringStrategy.Always } };

<DndContext sensors={sensors} collisionDetection={pointerWithin} measuring={measuring} ...>
  ...
  <DragOverlay dropAnimation={null} modifiers={[snapCenterToCursor]}>
    {overlay content}
  </DragOverlay>
</DndContext>
```
**Motivo:** bug de offset persistiu por 3 tentativas (largura fixa, MeasuringStrategy sozinha, dropAnimation null) até a combinação acima resolver definitivamente.
**Status:** vigente. Reaproveitar na esteira de Promoção de Consultores (`/esteira/promocao-consultores`).

### 2026-07-26 — Kanban com transições gated: modal de preenchimento obrigatório ao avançar etapa
**Decisão:** o Kanban da Esteira de Abertura de Unidades agora usa **transições gated** — o drag-and-drop não move o card diretamente; ele abre uma modal de preenchimento dos dados da etapa destino. O card só avança se o operador salvar; se cancelar, o card permanece na coluna original.

Padrão implementado (replicar na Esteira de Promoção de Consultores):

1. **Validação de sequência:** `KanbanBoard` compara `currentIdx + 1 === targetIdx`. Se o drop for em qualquer outra coluna, exibe `toast.error("Só é possível avançar para a próxima etapa.")` e o card volta.

2. **Prop `onRequestTransicao` (não `onMoverRegistro`):** o board emite `(registroId, etapaDestino)` em vez de mover diretamente. A página pai (`AberturaUnidadesKanbanPage`) controla o estado `transicaoModal: { registroId, etapaDestino } | null`.

3. **`EtapaTransicaoModal`** (`src/components/esteira/EtapaTransicaoModal.tsx`): componente genérico que renderiza formulário dinâmico por `etapaDestino` via `switch`. Props: `open`, `onOpenChange`, `etapaDestino`, `registroNome`, `onSalvar(data: TransicaoFormData)`. A interface `TransicaoFormData` unifica todos os campos possíveis de todas as etapas (campos opcionais por etapa).

4. **Caso especial COMITÊ (ramificação):** se `decisaoComite === "reprovado"` → card fica no COMITÊ com `status: "reprovado"` (não avança). Se `decisaoComite === "ajuste"` → card volta para `PLANO_NEGOCIO`. Só `"aprovado"` avança para DOCUMENTAÇÃO. Feedback visual na modal: alerta vermelho para reprovação, alerta amber para ajuste.

5. **Fluxo completo:** drag end → valida next-only → emite `onRequestTransicao` → pai abre modal → operador preenche → salva → `setRegistros` atualiza `etapaAtual` → toast de sucesso → modal fecha.

Arquivos envolvidos: `src/components/esteira/KanbanBoard.tsx`, `src/components/esteira/EtapaTransicaoModal.tsx`, `src/pages/AberturaUnidadesKanbanPage.tsx`.
**Motivo:** pedido do usuário — processo real exige preenchimento de dados a cada avanço de etapa, não movimentação livre.
**Status:** vigente. Reaproveitar na esteira de Promoção de Consultores.
